Skippy's existing 150-second claim lease, 30-second heartbeat and 15-minute execution ceiling are useful machinery, not a completed recovery guarantee. Claim currently advances nextDueAt; a crash does not automatically retry immediately. Require durable failed-window retry with bounded backoff (1, 5, 15 minutes, then next scheduled attempt), no coverage advancement, and a new fenced attempt. Fix the in-flight claim race and reject writes from expired/superseded workers. Connector availability must not fall back to broad Skippy credentials when the Agenda token is missing. Keep readiness failures explicit. These are proposed requirements, not changes made here.

## End-to-end data flow and storage contract

The following is the design to implement only after this gate passes. Where current APIs lack the necessary guarantees, that is called out rather than presumed implemented.

1. The single schedule owner obtains a Convex lease for a brain/source/account/scope and assigns `runId`, attempt, owner generation and immutable UTC `[windowStart, windowEnd)` bounds. Use a stable source/account identity; timezone is query/display context, not object identity. Include explicit DST and all-day-date handling.
2. Load the canonical ingestion skill and per-source checkpoint through scoped Skippy MCP. Resolve account/calendar inventory against the approved scope. A permission/scope change fails that source instead of turning it into an empty success.
3. Native Gmail/Calendar/Messages connectors enumerate every page in the frozen scope/window and read required content. Use connector-specific argument names. Record continuation state; a limit, repeated token, timeout, missing body or uncertain completeness yields partial/failed coverage. Do not use local database readers as a hidden fallback.
4. Normalize source identity, revision and source references before semantic extraction. Submit useful objects through existing Skippy ingestion with `rubricDecision` and `sourceRefs`; preserve existing accepted objects and user changes. Record a processed-source receipt even when the rubric produces no object, so “no extraction” is distinguishable from “not read.” Calendar mirror updates take the separate path below.
5. Process Home quick captures independently: list pending `remember` captures, ingest idempotently using the capture ID, acknowledge only after durable success. Exclude `hold` captures. Connector failure must neither discard captures nor make their success imply source coverage.
6. Commit each durable batch with receipts and fenced progress. Only after every page and required read/write in a source window succeeds advance that source's coverage boundary to the frozen window end. Final reporting follows the durable state. A crash after commit but before reporting replays safely.

**Checkpoint storage:** keep canonical state in Convex, never a worktree, prompt, Codex session or local file. Use versioned `sourceSyncStatuses` keys such as `ingestion:v2:<source>:<accountKey>:<scopeHash>` with brain scoping. Reserve existing `google_calendar:<calendarId>` metadata for the legacy mirror while it remains owner; semantic extraction must not overwrite its token. Store scope version, committed-through boundary, pending window and page continuation, attempt/run IDs, lease generation, last success, gap/backfill ranges, and completeness/reconciliation generation. OAuth secrets stay in connector/host credential storage; checkpoint metadata contains no credentials.

The current `knowledge.updateSourceSyncStatus` overwrites metadata without a compare-and-swap lease contract. `recordIngestionRun` inserts rows rather than finalizing an idempotent run ID. Therefore current generic reporting tools alone cannot implement atomic checkpoint/receipt commits. Proposed narrowly scoped MCP operations must enforce ownership, expected checkpoint version and server-side transaction boundaries; existing flexible metadata is not a concurrency protocol.

**Recovery:** retain the last complete boundary on failure. Persist bounded page work if the connector supports safe continuation; otherwise replay the same frozen window with receipts. Expired continuation restarts that window. The 15-minute overlap is a reread buffer, not a guarantee against arbitrarily late arrivals. Define and test a reconciliation sweep for older arrivals; if connector semantics cannot discover them, retain NO-GO. Split downtime into contiguous bounded backfill windows, oldest gap first, and report outstanding ranges. Never silently clamp away work older than 48 hours as the current role-level cursor does. First-run coverage starts at an explicitly recorded baseline; do not claim earlier history covered.

**Deduplication:** add durable, indexed source receipts keyed by brain/source/account/container/native item ID plus revision and extraction version. Receipt, object/source linkage and progress must commit atomically or use an idempotent staged-batch protocol that cannot advance coverage before writes. Gmail message ID is the item key; thread ID is grouping/context, not the dedupe unit. Calendar keys include account, resolved calendar ID and event/instance ID; retain recurrence master/original-instance identity and provider revision. Messages needs a proven stable item key before implementation. Content hashes can detect payload change but cannot replace native identity. Use source-to-object relationships for multiple facts from one message; replay must not create new tasks/events merely because generated wording differs. Backfill existing source identities with collision reports before enforcing new uniqueness, retaining canonical object IDs and legacy links.

## Calendar mirror and external writes

Semantic extraction and event synchronization are separate consumers. Home, overlap checks and duplicate warnings need a complete structured `calendarEvents` mirror, including events that produce no semantic task. Do not route mirrored events through generic `ingestObject` or manufacture duplicate events as extracted knowledge.

Keep `calendarMirrorSync.ts` and its ten-minute/startup loop until a replacement proves parity. Current full-resync horizon is 30 days back and 400 days forward, 250 results/page, 40-page cap, 100-event upsert batches. It uses `singleEvents: true`, `showDeleted: true`, sync tokens and one 410 resync attempt. Current cap handling returns “done” without a token and the caller records completed: this is not complete coverage and must not be inherited. A replacement must report truncation as incomplete and keep continuation/gaps visible.

Proposed replacement: native Calendar enumeration → scoped Skippy MCP structured mirror ingestion → normalized `calendarEvents` updates → Home/conflict consumers. Current mirror ingestion endpoints are host-authenticated (`hostUpsertCalendarEvents`, `hostRecordCalendarSyncToken`); a suitable Agenda-scoped MCP surface is required, not an assumption that `ingest_object` supplies it. Namespace identity by account/calendar, reject stale revisions, preserve origin, related entity links and snoozes, and settle echoes of Skippy-created events quietly. Current lookup by brain/source/external ID omits calendar identity; current patch planning does not compare remote revisions. Both need an explicit migration and tested conflict behavior.

For snapshot-based reconciliation, stage a generation and mark it complete only after exhaustive enumeration of exactly the same scope. Missing events must not be cancelled on partial results or permissions failures. Handle moved events and recurrence exceptions using stable identity and provider semantics. No proven native tombstone/reconciliation contract currently exists; a proposed snapshot algorithm does not close this blocker. Retaining the legacy mirror indefinitely would require a consciously reduced migration scope, not a passed full-retirement gate.

**Preserve the external calendar write chain:** Skippy `draftCalendarEvent` → `pendingActions` ready/`approved` compatibility state and minted provider event ID → `claimNextCalendarAction` → runner `calendarActionExecutor.ts` → `@skippy/gcal-write-mcp` auth/resource/insert libraries → Google → `recordCalendarActionResult`. Preserve leases, duplicate sweep, overlap warnings, 409-as-idempotent-retry behavior and echo handling. Older source comments describe human approval; current Home retirement design uses an automatic outbox. This migration does not reinstate a review gate or expand writes.

`google_write` enables both mirror and action loops today, and both share `createCalendarTokenSource`. Removing the slug, credentials, dependency or package breaks writes even if native reads work. Keep the write MCP wrapper too until its harness consumers are separately inventoried. This task authorizes no native calendar-write substitution, event deletion, consent change or credential revocation.
